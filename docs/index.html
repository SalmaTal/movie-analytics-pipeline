Pipeline de données TMDB

On construit un pipeline de données : une suite de scripts lancés dans l'ordre, où chaque script prend le résultat du précédent et l'améliore. Ici, on récupère des informations sur des films depuis TMDB, on les nettoie, on les range dans une base SQL et on les publie sur Hugging Face.

Le pipeline en un coup d'œil

TMDBLe site qui possède les infos sur les films
1
Fichiers brutsdata/raw/, JSON Lines : une copie exacte de ce que TMDB a répondu
2
Fichiers propresdata/processed/, Parquet : les mêmes infos, corrigées et rangées
3
Base PostgreSQLPour poser des questions en SQL
4
Hugging Face HubPour partager le dataset

Les étapes 3 et 4 partent toutes les deux des fichiers propres : Hugging Face ne dépend pas de la base de données.

Les 4 étapes

1RécupérerUn script demande à TMDB les infos de chaque film et les copie dans des fichiers.En cours 2NettoyerUn script corrige les données et sépare films, genres et acteurs.À venir 3RangerOn charge les données dans PostgreSQL et on les interroge en SQL.À venir 4PartagerOn publie les fichiers propres sur Hugging Face, avec une fiche descriptive.À venir

Pourquoi plusieurs scripts plutôt qu'un seul ?

  • On évite de tout recommencer. Si le nettoyage plante, on le relance sans redemander les données à TMDB.
  • On retrouve vite une erreur. Chaque étape garde son résultat : on voit où ça a déraillé.
  • On se répartit le travail. Une personne par étape.

Rendu final et planning

Ce qu'on rend
  • Le dépôt Git organisé, avec tout le code.
  • Le dataset publié sur le Hugging Face Hub.
  • Une présentation de 10 minutes : chaque membre parle, avec des chiffres mesurés (durées, volumes, RAM, gain de l'index).

Étape 1 sur 4 · Ingestion · A (Yannis)

① Récupérer les données

Un script demande à l'API TMDB les infos de chaque film et les écrit telles quelles dans des fichiers.

Avant : rien, c'est le point de départ.Après : ② Nettoyer lit les fichiers produits ici.

Entrée et sortie

EntréeL'API TMDB : /discover/movie pour la liste des films, puis /movie/{id}?append_to_response=credits pour chaque fiche.
Sortiedata/raw/, au format JSON Lines : un film par ligne, par exemple data/raw/movies/year=2010.jsonl.

Pourquoi garder une copie « brute » ?

On garde une copie exacte de ce que TMDB a répondu, sans rien modifier. Si le nettoyage a un bug, on le corrige et on le relance, sans redemander les données à TMDB. C'est aussi pour ça que data/raw/ n'est jamais modifié.

Ce que la fiche exige

aiohttp (asynchrone)Lancer plusieurs requêtes en même temps au lieu d'attendre chaque réponse une par une. Pour des milliers de films, c'est beaucoup plus rapide.
Un sémaphoreUne limite au nombre de requêtes simultanées, par exemple 20, pour ne pas surcharger TMDB et ne pas se faire bloquer.
Timeouts et nouvelles tentativesSi une réponse tarde ou échoue, on réessaie en attendant de plus en plus longtemps : 1 s, 2 s, 4 s...
Des noms prévisiblesLe nom du fichier dit ce qu'il contient : year=2010.jsonl. On le retrouve sans chercher.
Un checkpointLa liste des films déjà récupérés. Si le script s'arrête, il reprend là où il en était.

Où on en est

  1. Explorer l'API à la main avec Postman : fiche d'Inception et volumes de discover mesurés. Fait (reste à vérifier credits)
  2. Fixer le périmètre : 2000-2026, au moins 50 votes, en anglais (voir Pourquoi cibler). Fait
  3. Écrire la note d'exploration (contrat 1 avec B et C) : voir Note d'exploration. À valider en équipe
  4. Fournir un petit échantillon de JSONL à B pour qu'il démarre.
  5. Écrire le script asynchrone.
Étape 2 sur 4 · Transformation · B

② Nettoyer les données

Un script lit les fichiers bruts, corrige et range les données, puis écrit des fichiers propres. Les fichiers bruts ne changent jamais.

Avant : ① a écrit les fiches brutes de TMDB.Après : ③ et ④ partent des fichiers propres produits ici.

Entrée et sortie

Entréedata/raw/, au format JSON Lines.
Sortiedata/processed/, au format Parquet, un format compact pour les tableaux : movies/, movie_genres/, credits/.

Ce que fait le nettoyage

  • Séparer : films, genres et acteurs partent dans des tableaux distincts, car une case ne peut pas contenir une liste.
  • Typer : le texte "2010-07-15" devient une vraie date.
  • Traiter les valeurs inconnues : une durée ou un budget à 0 devient une case vide, sinon les moyennes seraient fausses.
  • Supprimer les doublons : un même film ne doit apparaître qu'une fois.

Ce que la fiche exige

  • Un traitement par lots : lire par paquets (par exemple 1 000 lignes), pour ne pas saturer la mémoire.
  • Un nettoyage et un typage des données.
  • Une sortie en Parquet.
  • Des tests avec pytest.

genresune ligne par genre

Les tables « pont » existent parce qu'un film a plusieurs genres et qu'un genre concerne plusieurs films. On y met une ligne par couple film-genre.

  • Un index dont on mesure le gain avec EXPLAIN ANALYZE.

L'API TMDB

Comprendre une API

Le script d'ingestion passe son temps à « parler » à TMDB. Avant d'écrire du code, il faut comprendre comment se passe cette conversation.

Ce qu'est une API

Une API est une adresse web faite pour les programmes, pas pour les humains. Le site de TMDB affiche une jolie page avec des images. L'API, elle, renvoie les mêmes informations en texte brut, au format JSON : des étiquettes et leurs valeurs.

GET https://api.themoviedb.org/3/movie/27205?api_key=TA_CLE

{"id": 27205, "title": "Inception", "release_date": "2010-07-15", "runtime": 148, ...}

GET veut dire « je veux lire une information ». C'est la seule méthode dont on a besoin avec TMDB.

Chemin et paramètres

/movie/27205  ?  api_key=...  &  language=fr-FR  &  append_to_response=credits
└── chemin ─┘     └─ param 1 ┘    └── param 2 ──┘    └────── param 3 ─────────┘
Le chemin, avant le ?Désigne la chose demandée : /movie/27205, c'est « le film 27205 ».
Les paramètres, après le ?Servent à filtrer ou régler la réponse : l'année, la langue, le tri, la page... Exemple : /discover/movie?primary_release_year=2010.

Le mécanisme des paramètres (nom=valeur séparés par &) est une règle du web, la même partout. Mais le sens de chaque paramètre est propre à chaque API, et c'est sa documentation qui le donne. Un paramètre inconnu est en général ignoré, sans erreur.

Les codes de réponse

CodeSensCe que le script fera
200Tout s'est bien passéÉcrire la réponse dans le fichier
401Clé refuséeS'arrêter : inutile de réessayer
404Ce film n'existe pasPasser au suivant
429Trop de requêtes, ralentisAttendre, puis réessayer
500, 503...Problème côté TMDBAttendre, puis réessayer

append_to_response : un appel au lieu de deux

Le casting n'est pas dans la fiche d'un film. On peut le demander à part (/movie/27205/credits) ou dans la même requête, avec append_to_response=credits.

Sans : deux allers-retours 
Toi → TMDB : fiche du film 27205
Toi ← TMDB : fiche
Toi → TMDB : acteurs du film 27205
Toi ← TMDB : acteurs
Avec : un seul aller-retour 
Toi → TMDB : fiche + acteurs du film 27205
     (TMDB va chercher les deux dans sa base
      et assemble un seul JSON)
Toi ← TMDB : fiche + bloc "credits"
  • C'est un seul appel : un seul clic sur Send, une seule réponse. Comme commander le plat et la boisson d'un coup au restaurant.
  • Le serveur ne garde rien en mémoire entre deux requêtes : il en fait juste un peu plus pour celle-ci.
  • Pourquoi c'est utile : chaque aller-retour prend 100 à 300 ms, et TMDB limite le nombre de requêtes par seconde. Pour 10 000 films, on passe de 20 000 requêtes à 10 000.
  • C'est propre à TMDB, pas une règle générale. D'autres API ont la même idée sous un autre nom (expand chez Stripe, include ailleurs). On peut en demander plusieurs : credits,keywords.

Le bon réflexe : lire la doc

Chaque API publie la liste de ses adresses et de leurs paramètres. Celle de TMDB : developer.themoviedb.org.

L'API TMDB

Les endpoints utiles

Un endpoint est une adresse précise de l'API : /movie/{id}, /discover/movie... TMDB en propose des dizaines, mais trois suffisent pour notre pipeline.

On part des données qu'on veut

Ce qu'on veut obtenir à la fin : un tableau de films, avec leurs détails, leurs genres et leurs acteurs. On cherche ensuite quels appels donnent ça. On part donc des données voulues pour choisir les endpoints, pas l'inverse. Pour analyser des séries, on aurait pris les endpoints /tv.

EndpointRôle dans le pipelineAppels
/discover/movieTrouver quels films récupérer : leurs ids1 par page de 20 films
/movie/{id} + creditsRécupérer tout sur chaque film, acteurs compris1 par film
/genre/movie/listLa liste des 19 genres (optionnel)1 seul

Pourquoi discover plutôt que les autres ?

C'est le seul qui permet de filtrer à volonté (par année, nombre de votes, langue...) et de parcourir tous les films qui correspondent.

Autre endpointCe qu'il faitPourquoi on ne le prend pas
/search/movie?query=...Chercher un film par son nomIl faut connaître le nom à l'avance
/movie/popular, /movie/top_ratedDes listes toutes faitesImpossible de découper par année
/trending/movie/weekLes tendances du momentChange chaque semaine, pas de filtre

À garder pour plus tard : /movie/changes liste les films modifiés récemment. La fiche parle de « mises à jour régulières » : il permettrait de ne redemander que les films qui ont changé. Bonne piste d'amélioration pour la présentation.

L'API TMDB

Les pièges repérés

Les points à garder en tête pour l'ingestion, et à transmettre à B pour le nettoyage.

Des 0 qui veulent dire « inconnu »budget, revenue et runtime valent souvent 0 pour les films peu connus. Ce n'est pas un vrai zéro : laissé tel quel, il fausserait les moyennes.
Des dates écrites en texte"2010-07-15" est du texte pour le JSON. Il peut aussi être vide ("") pour un film sans date connue.
Des listes dans une seule casegenres, cast, crew... Un tableau ne peut pas avoir une liste dans une case : il faudra les déplier en tableaux séparés.
La langue des textes Décidé : anglaislanguage=fr-FR traduirait title, overview et les noms de genres, mais les résumés français sont souvent vides. On demande donc language=en-US, écrit explicitement pour ne pas dépendre de la valeur par défaut de TMDB.
Une personne, plusieurs postesDans crew, Nolan apparaît comme Producer et comme Writer. Le couple film + personne n'est pas unique : c'est credit_id qui l'est. Et pour trouver les réalisateurs, on filtre sur job, pas sur known_for_department, qui est la spécialité habituelle de la personne.
Des valeurs nullimdb_id, belongs_to_collection ou les chemins d'images peuvent manquer. Le code ne doit pas planter dans ce cas.
Des listes qui bougentLe tri par popularité change d'un jour à l'autre. Deux lancements de discover ne donnent donc pas exactement les mêmes pages, d'où l'intérêt de dédoublonner les ids.

Cadrage

Pourquoi cibler

TMDB compte plus d'un million de films, sans parler des séries et des personnes. On ne récupère pas tout : on fixe un périmètre.

Pourquoi ne pas tout prendre ?

La qualitéLa grande majorité sont des courts métrages, des films amateurs ou des fiches presque vides : 0 vote, pas de durée, pas de budget.
Le tempsTMDB limite le nombre de requêtes par seconde. Tout récupérer prendrait des heures, pour des données en partie inutiles.
Le projetLa fiche demande un volume « suffisant pour justifier un pipeline », pas le maximum possible.

Les deux réglages du périmètre

Les années : 2000 à 2026 Décidé27 ans, de quoi analyser des évolutions dans le temps. On demande à discover une année à la fois. 2026 n'est pas terminée et ses films ont encore peu de votes : elle sera incomplète, ce qu'on signalera dans la Dataset Card.
Un seuil de 50 votes Retenu, à valider en équipevote_count.gte=50. Une note fondée sur 2 votes ne veut rien dire. Un seuil de 10 garde trop de fiches presque vides ; un seuil de 500 ne garde que les gros films. 50 est un compromis courant.

Les chiffres mesurés

Requête /discover/movieFilms (total_results)Pages (total_pages)
2010, sans seuil18 183910
2010, au moins 50 votes91646
2025, au moins 50 votes78340
  • Le seuil écarte 95 % des films de 2010 : surtout des fiches presque vides.
  • Sans seuil, 2010 dépasserait la limite de 500 pages : on ne pourrait pas tout récupérer en une recherche.
  • Volume attendu : environ 22 000 à 25 000 films sur 2000-2026 (2026 incomplète).
  • Une recherche par année suffit (46 pages au maximum), pas besoin de découper par mois.
  • Avec le casting, la table casting devrait dépasser 500 000 lignes : idéal pour mesurer le gain d'un index.

Hugging Face, sans IA

Il n'y a pas de machine learning dans ce projet, ni de prévision (forecast).

À quoi sert Hugging Face ici

Hugging Face est connu pour l'IA, mais on se sert ici de son Hub : c'est comme GitHub, mais pour les données. On y dépose notre dataset propre avec sa fiche descriptive, la Dataset Card. N'importe qui, à commencer par nous, peut ensuite le récupérer en deux lignes de Python :

from datasets import load_dataset
films = load_dataset("notre-groupe/tmdb-cinema", "movies", revision="v1.0.0")

Un projet de data engineering

Le data engineering est le métier qui consiste à construire le tuyau qui amène des données propres et fiables. Ce que d'autres en font ensuite (analyses, IA) vient après. Le dataset publié pourrait servir plus tard à prédire la note d'un film ou à recommander des films, mais c'est hors du périmètre. On peut le citer en « pistes d'amélioration » à la fin de la présentation.

Ce qu'on peut analyser

La fiche demande au moins 5 requêtes SQL d'analyse. Ces questions décideront aussi des champs à récupérer : on part des questions, puis on choisit les données.

QuestionDonnées nécessairesTechnique SQL
Quel genre a la meilleure note moyenne ?notes, genresjointure, GROUP BY
Les films sont-ils plus longs qu'avant ?durée, date de sortiewindow function (LAG)
Quels sont les 3 meilleurs films de chaque année ?notes, date de sortiewindow function (ROW_NUMBER)
Quels acteurs tournent le plus ?castingCTE, jointure
Quels genres sont les plus rentables ?budget, recettes, genresjointure, GROUP BY
Quels réalisateurs ont la meilleure moyenne ?équipe (crew), notesjointure, GROUP BY

La rentabilité ne se calcule que pour les films dont le budget et les recettes sont connus (pas à 0). Les réalisateurs demandent de garder crew, pas seulement cast. À décider : quelles questions on garde.

Organisation

Git, arborescence du dépôt et règles communes.

Git

  • Une branche par personne ou par fonctionnalité, fusionnée par pull request.
  • Relectures croisées : A relit B, B relit C, C relit A.
  • Ne jamais commiter .env ni data/.

Arborescence

movie-analytics-pipeline/
├── sql/                  # requêtes SQL (schéma, analyses, index)
├── scripts/
│   ├── ingest/           # ① récupérer
│   ├── transform/        # ② nettoyer
│   ├── load/             # ③ charger dans PostgreSQL
│   └── publish/          # ④ publier sur le Hub
├── data/                 # jamais dans Git
│   ├── raw/              # données brutes, jamais modifiées
│   └── processed/        # données propres (Parquet)
├── tests/                # tests pytest
├── docs/                 # cette doc et l'historique
└── README.md             # doc d'utilisation et Dataset Card

La structure de base est imposée par la fiche de la prof. scripts/load/, scripts/publish/ et docs/ sont nos ajouts.
